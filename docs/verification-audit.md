# Verification implementation map

Audit completed before verification implementation, 2026-10-07. Existing engine architecture is suitable; verification should drive it through the same choice boundary used by the client.

| Surface | Existing implementation and intended reuse |
| --- | --- |
| Authoritative state | `mtg-engine::state::GameState`: objects and players in `BTreeMap`, ordered zones, turn order, priority, combat, continuous effects, replacement/prevention state, triggers, Commander state, known information and RNG. Reuse rather than inventing another rules state. |
| Players and identity | `mtg-core::{PlayerId, ObjectId, CardId, AbilityId}`. A zone change creates a new object identity (CR 400.7); CardId identifies printed data, not a unique physical card. Owner/controller are separate; copied objects preserve `original`. |
| Actions and choices | `mtg-engine::{Action, Answer, Choice, ChoiceKind, LegalActions}` already serialize. `Engine::advance(&dyn PrintedCards)` returns `Progress`; `Engine::answer(cards, choice_id, answer)` validates submissions. Record every answer, including targets, ordering and optional costs. |
| Priority and stack | `GameState::priority`, `consecutive_passes`, and `zone_order[ZoneRef::shared(Zone::Stack)]`; cast contexts contain modes, targets, bindings and payments. Stack order is bottom to top. |
| Zones | `mtg-core::{Zone, ZoneRef}` declare shared/hidden/ordered zones. Libraries, stack and graveyards are ordered. Membership is in `GameObject::zone`, with an additional ordered index. |
| RNG and shuffle | `state::Rng` is deterministic SplitMix-style state with Fisher–Yates shuffle. `mtg-net::fairness` independently creates initial shuffle order from committed 32-byte seeds; `mtg-session::game::{game_seed,new_game}` derives per-seat/per-game seeds and seeds later engine shuffles. Production OS randomness exists in networking seed creation, outside engine execution. |
| Events | `Engine::log: Vec<mtg-core::StampedEvent>` includes sequence, cause and `Event`; `apply`, `detect`, `triggers`, `sba`, `resolve`, `layers`, `targeting`, `mana`, `cost`, `combat` and `turn` already expose the rules primitives to verify. Keep cause/event semantics in golden assertions. |
| Replay | Source comments promise replay, but the audit found no durable replay/scenario artifact or executable replay runner. Event application alone cannot reconstruct private engine continuations. The headless trace loop is a reusable bounded driver, not a replay implementation. |
| Hidden information | `mtg-engine::view::{PlayerView,project}`, and `Engine::view_for` for choice-specific projection. Projection excludes ordered libraries, opponent hands and private cast machinery; reveal/look history is separately represented. `PlayerView` is the network serialization boundary. |
| Cards and compiler | `mtg-ir::cards::PrintedCards` is the engine interface. `mtg-session::game::GameCards` already serializes complete sourced/compiled game card data. `mtg-oracle::compile::{FaceText,Compiled,compile,card_understood}` explicitly tracks unsupported text. Reuse these interfaces and pin fixture card data instead of depending on the mutable SQLite catalog. |
| Integration and fixtures | `mtg-engine/tests/` contains focused rules, mana, combat, targeting, trigger/APNAP, Commander, cleanup, undo, etc.; `tests/common/mod.rs` supplies card/engine helpers. `mtg-oracle/tests/compiled/` exercises compiler-to-engine behavior via its harness. Deck/store/import suites validate other boundaries. Existing Rust fixtures are extensive, but there is no versioned replay/regression corpus. |
| Network | `mtg-net` covers wire JSON, authenticated/encrypted channels, fairness, discovery and invitation handling; tests include `socket.rs` and `encryption.rs`. `mtg-session/tests/{play,over_socket}.rs` exercise authoritative host and projected guest choices/views. Preserve host authority and never send canonical full state to guests. |
| CI | `.github/workflows/release.yml` currently runs Python release tests, `cargo fmt --all -- --check`, all-feature workspace tests, and all-target/all-feature Clippy before release. No PR verification workflow, scheduled campaigns, property dependency, fuzz workspace, confidence ledger or mutation campaign was present at audit time. |

## Foundation design constraints

1. A `GameState` digest is not an `Engine` checkpoint. Pending choices, suspended resolution/announcement, trigger ordering queues and turn-based-action flags live privately in `Engine`. Use initial state plus ordered answers to reconstruct execution, and include current choice/status at observable checkpoints. Restrict arbitrary initial snapshots to documented quiescent boundaries; do not claim resumability from mid-resolution state alone.
2. Timestamps are rules data: continuous-effect order, dependency behavior and upkeep comparisons depend on them. Remove wall-clock/log decoration only. Do not erase `GameObject::timestamp`, effect timestamps, RNG state, last-known information or histories used by trigger detection.
3. Preserve ordered libraries, stack, graveyards, turn/APNAP order, prevention shields and continuous-effect insertion/order. Deterministic `BTreeMap` iteration already helps. Object-id normalization, if added later, must consistently rewrite every reference including last-known objects, triggers, bindings and attachments; indiscriminate sorting can change behavior.
4. JSON cannot encode non-string map keys such as `ZoneRef` or `(ObjectId, AbilityId)` directly. A deliberate sequence-of-pairs encoding or a Rust-friendly format is needed; do not silently drop these fields to make serialization work.
5. Validate fixtures before constructing an engine: supported format/rules/build compatibility, card-data hash, unique players/objects, ownership/controller existence, correct shared/player zone shape, no duplicate or dangling ordered-zone memberships, ordered-zone completeness, turn order and active/priority players, cards/faces and bounded sizes. A deserialize success is not state validity.
6. Bound file bytes, actions, cards, objects and engine advancement between choices. Malformed and malicious fixtures must produce errors instead of stalls or unbounded allocations. Divergence should identify the submitted answer/action index, expected and actual choice/state, and first differing field.
7. Full canonical artifacts include both libraries and opponent hands. They are private bug-report attachments and post-game artifacts, never a new network message or live public export. Hidden-information checks should cover cards, faces, object ids, ordering, legal targets and suspended announcement/resolution views—not only hand size.
8. Seed and final digest alone cannot locate the first altered transition. Record per-answer/checkpoint expected digests or canonical checkpoints, plus the final digest; checksummed card data and a declared digest schema/rules version prevent false comparisons across intentional changes.
9. Mutation experiments should run against copied source or a dedicated isolated worktree and must prove that the suite ran and failed for the intended reason. Never manufacture mutation/confidence counts from configured campaign budgets. Independent reviewer acceptance must remain distinct from Builder-authored tests.

## Incremental validation plan

Start with canonical serialization/determinism and strict fixture round trips, then record real engine choices in two-player and multiplayer fixtures. Independently challenge zero-toughness SBA versus destruction, hidden-hand projection and first-checkpoint replay divergence. Add bounded generated legal actions and structural validation failures before expanding reference models and confidence reporting. Keep unavailable campaigns and unsupported mechanics explicitly unverified.

## CI and release assessment policy

`verification.yml` runs PR checks plus scheduled nightly/weekly budgets. `scripts/verification_campaign.py` saves observed command results, requested property budgets, deterministic seeds and semantic reproductions; nightly/weekly add bounded libFuzzer, and weekly runs isolated production mutation checks. Requested budgets do not imply completed case counts. Empty replay or regression corpora fail the campaign.

`verification.json` is the explicit known-issues manifest. Initial serious-category assessments are **unassessed**, represented as unknown counts, not zero. A known open state-corruption, network-divergence or silently unsupported-rules issue blocks ordinary PR/release gates. The release workflow's explicit `closed_alpha` dispatch input additionally requires reviewed assessments with reviewer/evidence provenance and zero known open violations. Ordinary automated releases remain possible without claiming closed-alpha verification or VERIFIED confidence. No script automatically promotes a primitive or card to VERIFIED.

Campaign reports and private reproductions are archived for failed runs as well as successful runs. Structural fuzzing does not yet exercise SQLite saves, encrypted transport framing or packet-loss/reconnect campaigns. Real-deck and independent external-engine campaigns remain explicitly unavailable; nightly/weekly budgets are bounded experiments, not a claim of millions of completed games.

Repository administrators must mark the `Verification / verify` check required in branch protection (or a ruleset) to prohibit merges after failed checks. Adding a workflow does not itself configure GitHub merge protection.

## Independent leave-game review

The independent reviewer read [the official CR effective September 25, 2026](https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.txt), especially 800.4a/d and 113.7a. `crates/mtg-engine/tests/leave_game_review.rs` now supplies seven behavioral checks: removal across zones and views, surviving activated abilities, simultaneous elimination with layered control, restoration to a surviving controller, residual foreign-owned permanent exile, delayed-trigger controller handling, and survival of resolved noncontrol effects. Control fixtures use `layers::layer::CONTROL` and assert the intended controller before elimination, preventing a fixture with an inactive layer from passing accidentally.

The surviving-ability case independently reproduced a genuine defect: removing the source owner's objects also removed another player's activated ability. The Builder corrected it; all seven independent checks pass afterward. These are bounded acceptance checks, not comprehensive verification of multiplayer rules or a VERIFIED confidence promotion.

## Independent targeting review

The reviewer independently read 601.2c, 608.2b and 115.5 in the [official June 19, 2026 rules PDF](https://media.wizards.com/2026/downloads/MagicCompRules%2020260619.pdf); the September TXT endpoint was unavailable during this review. `crates/mtg-engine/tests/targeting_review.rs` contains ten acceptance cases. Five initially failed: valid distinct-target assignments hidden by greedy selection, player qualifiers ignored during resolution, nonadjacent duplicate targets accepted within one occurrence, nonexistent targets silently replaced, and a multi-object group's second target checked against a subsequent player's specification. The Builder corrected these defects; all ten checks pass.

The other checks protect source-versus-stack identity, self-targeting prohibition, leave/reenter identities, departed players, and legal reuse across separate target occurrences. Invalid-answer checks also require retaining the original question and accepting a subsequent valid answer. This establishes bounded independent acceptance, not complete targeting verification or VERIFIED status.
